# AI Knowledge Base Assistant

> A Retrieval-Augmented Generation (RAG) assistant that turns uploaded PDF and TXT documents into a searchable knowledge base and answers questions with grounded, source-cited responses.

---

## 1. Overview

**AI Knowledge Base Assistant** lets a user upload documents, automatically indexes them for both semantic and keyword search, and answers natural-language questions using only the content of those documents. Every answer is generated with an explicit instruction to the LLM to avoid speculation, and the pipeline verifies that cited sources actually exist among the retrieved chunks before returning a response.

The user interacts with the system through a Streamlit UI that talks to a FastAPI backend over HTTP. A typical session looks like: upload documents → the backend extracts, chunks, and embeds the text → ask a question → the backend retrieves relevant chunks using a hybrid of vector similarity and keyword matching → an optional LLM-based reranking step reorders the results → Gemini generates a structured, cited answer from that context.

RAG is used here specifically because the assistant is meant to answer questions about a private set of documents (e.g. company policies) rather than general knowledge — grounding answers in retrieved text reduces the risk of the model inventing policy details that were never actually written down. What makes this particular implementation technically interesting is the combination of **hybrid retrieval** (FAISS + BM25), an **LLM-based reranker**, a **guardrail layer** that verifies citation grounding after generation, and a **lightweight evaluation harness** for measuring retrieval and answer quality against a fixed question set.

> This is a project-scale implementation intended to demonstrate a complete RAG system end-to-end. It is not hardened for multi-tenant production traffic — see [Limitations](#21-limitations) for details.

## 2. Key Features

### Document Management
- Upload PDF and TXT files (individually or in sequence) through the API or Streamlit UI
- Text extraction via PyMuPDF (PDF) with page-level metadata
- Overlapping chunking with configurable chunk size and overlap
- Per-document and per-knowledge-base statistics (document count, chunk count, sources)
- Ability to list or clear all processed documents

### RAG & Retrieval
- Gemini embeddings for semantic search
- FAISS (`IndexFlatL2`) vector index
- BM25 (`rank-bm25`) keyword index
- Hybrid search combining normalized semantic and keyword scores with configurable weights
- Optional LLM-based reranking of the top candidates
- Optional LLM-based query transformation (generates alternative phrasings before retrieval)

### AI & Conversation
- Answers generated by a configurable Gemini model with a strict grounding system prompt
- Structured output parsing (answer, key points, confidence, sources) with multiple fallback parsers
- Session-based conversation memory with a configurable message window
- Simulated word-by-word streaming endpoint for the chat UI
- Explicit "no information in the uploaded documents" response when the knowledge base is empty or no relevant chunks are found

### Tools & Guardrails
- A small tool registry exposing `search_documents`, `get_document_stats`, and `list_documents`
- API-key authentication on all document, chat, and tool endpoints
- Input validation (query length, empty queries) and basic prompt-injection pattern detection
- File type and file size validation on upload
- Post-generation grounding check that rejects/flags answers whose cited sources don't match retrieved chunks

### Evaluation
- A fixed JSON test-question set with expected sources and keywords
- An evaluator that runs each question through the live pipeline and scores retrieval accuracy, source accuracy, keyword coverage, answer grounding, and confidence calibration

### Deployment & Engineering
- FastAPI backend with automatic OpenAPI/Swagger docs
- Streamlit frontend
- Dockerfile and Docker Compose for running both services together
- Health-check endpoint reporting model configuration and knowledge-base size
- Centralized structured logging and a typed application error hierarchy
- Automated test suite covering the API, RAG components, memory, tools, and guardrails

```text

 ▼

 ▼
```

> **Note on persistence:** each document upload is written to `data/processed/` on disk. However, the FastAPI dependency layer (`api/dependencies.py`) constructs the `RAGPipeline` with `load_persisted=False`, so the in-memory index starts **empty on every application restart** — persisted files are not automatically reloaded on startup in the current configuration. See [Limitations](#21-limitations).

## 4. RAG Pipeline

### Ingestion
1. **Validation** — file extension (`.pdf`/`.txt`) and size (`MAX_UPLOAD_SIZE_MB`) are checked before processing.
2. **Extraction** — PDFs are parsed page-by-page with PyMuPDF; TXT files are read directly (with a `latin-1` fallback if UTF-8 decoding fails).
3. **Chunking** — text is split into overlapping segments (`CHUNK_SIZE` / `CHUNK_OVERLAP`), preferring sentence or word boundaries, capped at 50 chunks per document call to control embedding cost.
4. **Embedding** — chunks are embedded in small batches via the Gemini embeddings API, with retry/backoff on quota errors.
5. **Indexing** — chunks and embeddings are added to both the FAISS index and the BM25 index, with duplicate chunk IDs filtered out.
6. **Persistence** — both indexes are pickled/serialized to `data/processed/`.

### Retrieval
1. The query (or, if query transformation is enabled, several alternative phrasings) is embedded and searched against FAISS for semantic matches, and tokenized and searched against BM25 for keyword matches.
2. Scores from both methods are independently normalized, then combined using `SEMANTIC_WEIGHT` and `KEYWORD_WEIGHT`.
3. Results below a minimum combined-score threshold are dropped, and the remainder are deduplicated and sorted.
4. If reranking is enabled and there are more candidates than the target `final_k`, an LLM call re-orders the top candidates by relevance before the final top-k is selected.

**Why hybrid retrieval?** Semantic (FAISS) search is good at matching meaning and paraphrasing but can miss exact terms — policy numbers, specific dates, or named fields — that a keyword search (BM25) catches directly. Combining both with tunable weights lets the system favor whichever signal is stronger for a given query rather than relying on a single retrieval strategy.

### Generation
1. The final chunks are formatted into a context block with source/page attribution, alongside recent conversation history.
2. A system prompt instructs the model to answer **only** from the provided context, distinguish permitted vs. mandatory policy language, cite sources, and assign a confidence level.
3. Gemini generates a response, which is parsed into a structured `answer / key_points / confidence / sources` object using a cascade of JSON, markdown-JSON, regex-extraction, and plain-text fallback parsers.
4. A guardrail step verifies that every cited source actually appears among the retrieved chunks before the answer is returned; if grounding fails, the response is still returned but flagged with a warning.

## 10. Using the Application

1. Start the FastAPI backend and the Streamlit frontend.
2. In the Streamlit sidebar, confirm the **Backend URL** and enter your **API Key** (must match `API_KEY` in `.env`), then click **Save**.
3. Go to the **Knowledge Base** page and upload one or more PDF/TXT documents.
4. Click **Process Documents** and wait for confirmation; check the **Statistics** panel for document/chunk counts.
5. Switch to the **Chat** page and ask a question about the uploaded content.
6. Review the answer along with its **confidence** level, **key points**, and cited **sources**.
7. Ask a follow-up question in the same session to see conversation memory in effect.
8. Ask a question unrelated to the uploaded documents — the assistant should respond that it doesn't have enough information rather than guessing.

Example questions (based on the bundled evaluation set):

- "What are the standard working hours?"
- "Is remote work allowed?"
- "What is the company policy on vacation days?"
- "How many sick days are employees allowed?"
- "What is the dress code for the office?"

## 12. Tool Calling

Three tools are registered in `tools/tool_registry.py`:

| Tool                | What it does                                                              |
| -------------------- | --------------------------------------------------------------------------- |
| `search_documents`    | Runs a hybrid search against the knowledge base and returns matching chunks |
| `get_document_stats`  | Returns document count, chunk count, and per-document chunk breakdown       |
| `list_documents`      | Returns the list of processed document filenames                            |

Tools are exposed both via the `/api/tools/*` endpoints (explicit invocation) and via `/api/tools/execute`, which routes to `ToolRegistry.execute_tool` after basic parameter-type validation.

Within the chat endpoint (`api/routes_chat.py`), tool invocation is **not** autonomous LLM function-calling — it is a simple keyword trigger: if the user's message contains `"search for"` or `"find"`, the backend calls `search_documents` directly and attaches the result to the response as `tool_calls`. The LLM itself does not decide when to call a tool in the current implementation.

## 13. Conversation Memory

Conversation state is managed per session by `memory/conversation_memory.py`:

- Each session gets a `ConversationMemory` object identified by a UUID `session_id`, created on the first chat request and reused on subsequent requests with the same ID.
- Messages are stored with role (`user`/`assistant`), content, a timestamp, and optional metadata (assistant messages store `sources` and `confidence`).
- The history is trimmed to the most recent `MAX_MEMORY_MESSAGES` entries.
- On each new question, the trimmed history (excluding the just-added current message) is formatted into the prompt so the LLM has conversational context.
- Memory is held **in-process** (a dictionary keyed by `session_id`) — it is not persisted to disk and does not survive an application restart. `MemoryManager.cleanup_old_memories()` exists to prune stale sessions but is not currently scheduled automatically.

## 14. Security & Guardrails

- **API-key authentication** — all chat, document, and tool endpoints require a valid `X-API-Key` header matching `API_KEY` in the environment.
- **Input validation** — queries must be between 3 and 500 characters; empty queries are rejected.
- **Prompt-injection pattern detection** — queries containing phrases like "ignore previous instructions", "you are now", "system prompt", "jailbreak", etc. are rejected before reaching the LLM.
- **File validation** — uploads are restricted to `.pdf`/`.txt`, checked against `MAX_UPLOAD_SIZE_MB`, and rejected if empty.
- **Output grounding verification** — after generation, `OutputGuardrails.verify_grounding` checks that every source the model cited actually corresponds to a retrieved chunk; ungrounded answers are flagged with a warning rather than silently trusted.
- **Structured error handling** — a typed `AppError` hierarchy (`DocumentProcessingError`, `RetrievalError`, `LLMError`, `AuthenticationError`, `ValidationError`) maps to consistent HTTP status codes and JSON error bodies.
- **Secret management** — the Gemini API key and application API key are read from environment variables, never hardcoded.

## 15. Cost Optimization

The pipeline includes several mechanisms aimed at reducing unnecessary Gemini API usage:

- **Query embedding cache** — repeated queries within a session reuse a cached embedding instead of calling the API again.
- **Batched embedding calls** — document chunks are embedded in batches of 5 rather than one call per chunk.
- **Retry with backoff** — embedding and generation calls retry on `429`/quota errors with increasing delay instead of failing immediately.
- **Chunk cap per document** — chunking is capped at 50 chunks per document to bound embedding volume for very large files.
- **Configurable output token limit** (`MAX_OUTPUT_TOKENS`) and **low default temperature** (`TEMPERATURE=0.2`) — keep generations focused and bounded in length.
- **Optional query transformation** — disabled by default (`use_query_transformation=False`), since it triggers an extra LLM call per question when enabled.
- **Reranking cap** — the reranker only considers a maximum of 10 candidate chunks per call, regardless of how many were retrieved.

> Even with these optimizations, Gemini API quotas and rate limits still apply and can affect usage under heavy load — this project does not provide unlimited or quota-free usage.

## 16. RAG Evaluation

`evaluation/test_questions.json` contains a fixed set of questions, each with expected source documents and expected keywords, grouped by category (currently `"policy"`).

`evaluation/evaluator.py`'s `RAGEvaluator` runs each question through the live pipeline and computes, via `evaluation/metrics.py`:

- **Retrieval accuracy** — F1 overlap between retrieved and expected sources
- **Source accuracy** — proportion of cited sources that were actually retrieved
- **Keyword coverage** — proportion of expected keywords present in the generated answer
- **Answer grounding** — word-overlap ratio between the answer and the retrieved chunk text
- **Confidence accuracy** — a simple calibration score based on the reported confidence level

Results are averaged overall and per category. There is no bundled CLI script to run evaluation from the command line — it is invoked programmatically, e.g.:

```python
from rag.pipeline import RAGPipeline
from evaluation.evaluator import RAGEvaluator

pipeline = RAGPipeline(load_persisted=True)  # or False, depending on your setup
evaluator = RAGEvaluator(pipeline, test_questions_file="evaluation/test_questions.json")
summary = evaluator.run_evaluation()
print(summary)
```

## 19. Deployment

This project is dockerized and includes a health endpoint, but a few things are worth understanding before running it beyond local development:

- **Persistence** — as noted in [System Architecture](#3-system-architecture), the default dependency wiring starts the RAG pipeline fresh (`load_persisted=False`) on every process restart, even though indexes are saved to disk after each upload. For a deployment where the knowledge base should survive restarts, this needs to be changed to `load_persisted=True` (or the indexes need to be loaded through another mechanism).
- **Storage** — FAISS and BM25 indexes are stored as local pickle/index files under `data/processed/`; there is no distributed or managed vector database. In a multi-instance deployment, each instance would have its own independent index unless the volume is shared.
- **API key security** — authentication is a single shared `X-API-Key` compared against one configured value; there is no per-user authentication, token expiry, or rate limiting built in.
- **Environment variables** — all configuration is environment-driven via `config/settings.py`, which makes it straightforward to inject different config per environment (dev/staging/prod) without code changes.
- **Health endpoint** — `/health` reports model configuration and current document/chunk counts, suitable for basic liveness/readiness checks.
- **Logging** — structured console logging is configured via `LOG_LEVEL`; there is no log shipping or centralized log aggregation built in.
- **Rate limits** — Gemini API quotas apply regardless of deployment target; the retry/backoff logic in `rag/embeddings.py` handles transient `429` errors but does not eliminate quota limits.

## 20. Limitations

- Depends entirely on the Google Gemini API for both embeddings and generation — outages or quota exhaustion on that API directly affect the assistant.
- The default dependency configuration does **not** reload persisted FAISS/BM25 data on startup, so the knowledge base is effectively session-scoped unless `load_persisted=True` is set explicitly.
- Vector and keyword indexes are stored as local files, with no distributed or managed vector database.
- Authentication is a single static API key with no per-user accounts, roles, or token expiry.
- Only PDF and TXT files are supported; scanned/image-only PDFs are not OCR'd, so text extraction will return little or no content for them.
- Tool invocation in chat is keyword-triggered rather than driven by autonomous LLM function-calling.
- The chat "streaming" endpoint splits an already-complete answer into word-sized chunks for the UI rather than streaming tokens directly from the Gemini API as they're generated.
- Conversation memory is held in-process and is lost on restart; it is not persisted.

## 21. Future Improvements

The following are realistic directions for extending the project — not implemented features:

- Load persisted indexes on startup by default (or add a dedicated "reload knowledge base" endpoint) for durable multi-session use
- Managed/distributed vector database (e.g. Pinecone, Qdrant, pgvector) in place of local FAISS files
- PostgreSQL or similar for document/session metadata instead of local pickle files
- Background/async document processing for large uploads
- Per-user authentication and accounts instead of a single shared API key
- OCR support for scanned PDFs
- Support for additional document formats (DOCX, HTML, Markdown)
- Observability/monitoring integration (structured metrics, tracing)
- A larger, more diverse evaluation dataset with automated regression tracking
- Configurable LLM provider abstraction (beyond Gemini)
- A production task queue for embedding/generation workloads
